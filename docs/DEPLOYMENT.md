## 1. 环境配置规范

### 1.1 服务器配置要求
| 节点类型 | CPU | 内存 | 存储 | 网络带宽 | 操作系统 | 数量 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Nginx / 前端** | 4核 | 8GB | 50GB SSD | 10Mbps | CentOS 7.9+ / Ubuntu 20.04+ | 2台 (主备) |
| **Node.js 后端** | 8核 | 16GB | 100GB SSD | 内网万兆 | CentOS 7.9+ / Ubuntu 20.04+ | 2台 (负载均衡) |
| **MySQL 数据库** | 8核 | 32GB | 500GB NVMe | 内网万兆 | CentOS 7.9+ / Ubuntu 20.04+ | 1主1从 |

### 1.2 运行时环境与依赖版本
- **Node.js**: v18.17.0+ (LTS)
- **Nginx**: v1.24.0+
- **MySQL**: v8.0.30+
- **PM2**: v5.3.0+ (用于后端进程守护)
- **前端构建**: Node v18+, pnpm v8+

### 1.3 环境变量配置标准
> **隔离机制**：生产环境（Production）与测试环境（Test）的 VPC 网络必须严格物理/逻辑隔离，生产环境变量文件 `.env` 必须由运维通过统一配置中心（如 Nacos/Apollo）或 CI/CD 注入，禁止代码仓库明文提交。

**后端生产环境变量 (`backend/.env`) 示例**：
```env
# 基础服务配置
NODE_ENV=production
PORT=3000

# 数据库连接 (走内网IP)
DB_HOST=10.0.0.100
DB_PORT=3306
DB_USER=prod_warning_admin
DB_PASSWORD=******** # 由密码库管理
DB_NAME=warning_system

# 安全密钥
JWT_SECRET_KEY=******** # 必须为 64 位以上高强度随机字符串
```

## 2. 详细上线操作流程

> **依赖关系声明**： 数据库迁移 -> 后端代码部署 -> 前端代码部署 -> 缓存/域名切换

### 2.1 数据库迁移 (Data Migration)
1. **备份策略**：使用 `mysqldump` 对主库进行全量备份，备份文件存储至 OSS。
2. **执行顺序**：
   - 登录生产库执行 DDL 脚本（建表、加索引）。
   - 执行 DML 脚本（初始化基础字典数据）。
3. **一致性验证**：执行 `SELECT COUNT(*)` 对比关键表数据量，检查慢查询日志。

### 2.2 后端部署 (Node.js API)
1. **代码拉取**：从 GitLab 拉取对应 `release` 分支代码。
2. **依赖安装**：在 `backend` 目录下执行 `npm ci --production`。
3. **配置文件更新**：拉取最新的 `.env` 配置文件并验证。
4. **服务启停控制**：
   ```bash
   # 使用 PM2 平滑重启
   pm2 reload warning-api --update-env
   ```
5. **健康检查**：调用内部 `/health` 接口，要求返回 HTTP 200。

### 2.3 前端代码打包与部署
1. **构建工具与参数**：
   ```bash
   # 在 admin 目录下执行
   pnpm install
   pnpm run build:pro # 触发 vue-tsc && vite build
   ```
2. **产物验证**：检查 `dist` 目录下是否生成了 `index.html` 及 `assets` 目录，检查 JS 产物体积是否在合理范围内。
3. **静态资源同步**：将 `dist` 目录打包通过 `scp` 或 rsync 推送至 Nginx 服务器。
4. **Nginx 配置重启**：
   ```bash
   nginx -t # 检查语法
   nginx -s reload # 平滑重载
   ```

### 2.4 负载均衡与网络切换
1. **负载均衡 (SLB/ALB)**：在云厂商控制台，将流量逐步导入新部署的后端节点节点，权重策略初始为 10%，观察 5 分钟无异常后调至 100%。
2. **CDN 缓存刷新**：在云控制台刷新前端静态资源 CDN 缓存（`https://cdn.domain.com/assets/*`），预计生效时间 3-5 分钟。
3. **域名切换**：如涉及新旧系统域名割接，修改 DNS 记录 A 记录指向新的 SLB，TTL 设置为 60s。

## 3. 回滚方案制定 (Rollback Strategy)

### 3.1 回滚触发条件 (满足任一即触发)
- 核心功能（如登录、报警推送）不可用持续超过 5 分钟。
- 后端 API 接口 5xx 错误率突增超过 10%。
- CPU/内存 持续 100% 导致系统拒绝服务。

### 3.2 快速回滚执行流程
1. **决策机制**：由项目经理或技术总监下达回滚指令，运维总负责执行。
2. **前端回滚**：将 Nginx 的 `root` 目录指向上一次的备份文件夹（如 `dist_bak_v0.9.9`），执行 `nginx -s reload`。
3. **后端回滚**：执行 `pm2 revert warning-api` 回退到上一个可用版本。
4. **数据回滚**：如无破坏性 DDL，不建议回滚数据库；若存在破坏性更新，从 OSS 拉取上线前 10 分钟的全量备份包进行覆盖导入。

### 3.3 回滚验证
- 回滚后，测试人员执行 P0 级冒烟测试用例，确认系统恢复到上线前状态。

## 4. 监控告警体系

### 4.1 监控指标与 Dashboard
采用 **Prometheus + Grafana** 体系：
- **系统性能**：CPU 利用率、内存使用率、磁盘 I/O、网络流入流出。
- **业务指标**：实时在线用户数、每分钟产生的预警记录数。
- **接口指标**：QPS、API 响应时间 (P95, P99)、HTTP 状态码分布。

### 4.2 告警规则与响应机制
| 告警级别 | 触发条件 | 通知方式 | 处理时效 |
| :--- | :--- | :--- | :--- |
| **P0 (灾难)** | 数据库宕机、API大面积5xx | 电话语音、钉钉/企微强提醒 | 5 分钟内响应，30分钟内解决或降级 |
| **P1 (严重)** | API 响应时间 P95 > 3s，CPU > 90% | 短信、钉钉/企微消息 | 15 分钟内响应 |
| **P2 (警告)** | 磁盘空间占用 > 80% | 邮件、工作群消息 | 2 小时内处理 |

## 5. 性能验证测试

### 5.1 性能基线标准
- **并发用户数**：支持 500 并发在线操作。
- **响应时间**：首页加载 < 1.5s，核心 API 接口响应 < 300ms。
- **吞吐量 (TPS)**：单节点支持 > 1000 QPS。

### 5.2 压测流程
使用 **JMeter** 或 **K6**：
1. 避开业务高峰期（建议凌晨 2:00 - 4:00）。
2. 执行压测脚本，模拟 500 虚拟用户持续发起请求 15 分钟。
3. 观察资源瓶颈，若出现性能下降，通过 Node.js 内存快照 (`heapdump`) 定位内存泄漏，或通过 `EXPLAIN` 分析慢 SQL。

## 7. 风险控制措施
1. **风险评估**：如果数据库迁移脚本耗时过长，可能导致业务中断。
2. **应对方案**：针对大表加字段/索引操作，必须采用 `pt-online-schema-change` 等工具实现在线无锁变更。
3. **沟通机制**：建立专属的【发布上线沟通群】，每个节点（开始打包、开始切流、发布完成）均需在群内通报。
4. **时间窗口**：强制要求在业务低谷期（每周四凌晨 2:00）执行变更。
